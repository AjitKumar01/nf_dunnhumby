Scoring a whole basket

The existing model cannot answer "is this basket of n products plausible for this customer?". Several things about it look like shortcuts, and they are — but they are all shortcuts around one obstacle. This document tests whether that obstacle is real. It is not, and removing it costs about an hour of compute per fit rather than the hundred-plus hours a naive attempt would take.

1One obstacle, five shortcuts

The model scores a basket S with a number E(S), and turns scores into probabilities the usual way — divide by the total over everything that could have happened:

P(S) = exp E(S)Z,     Z = ∑S′ exp E(S′)

"Everything that could have happened" means: keep the basket's shape — the same categories, the same number of items taken from each — and swap in different products. For a typical basket that is about 5 million alternatives. The 90th percentile is 1028.6. The largest measured is 10124.

You cannot add up 10124 numbers. Every awkward feature of the current model descends from that one fact:

2Why the sum looks impossible

The score has two parts:

E(S) = ∑j ∈ S bj  +  λ ∑{j,k} ⊂ S φj⊤φk

The first is each item's own appeal — harmless, because it splits cleanly across items. The second is a term for every pair, where φj is item j's embedding vector and λ is a scale factor. That is the obstacle: every pair involves two items, so no item can be chosen independently of the others.

Rewrite the pair sum using the schoolbook identity (a+b+c)² = a²+b²+c² + 2(ab+ac+bc):

∑{j,k} ⊂ S φj⊤φk = ½ ( ‖ ∑j ∈ S φj ‖² − ∑j ∈ S ‖φj‖² )

The right-hand piece is per-item and harmless. All of the difficulty is now in a single object: the squared length of a sum of vectors. Folding the harmless piece into the per-item appeal and writing cj = bj − (λ/2)‖φj‖²,

E(S) = ∑j ∈ S cj + ½‖v‖²,     v = √λ ∑j ∈ S φj

Why λ being a constant is what makes this legal

λ = 1/(n−1), where n is the number of items in the basket. That looks like it depends on S — but the sum defining Z runs only over baskets of the same shape, and the shape fixes n. So within the sum, λ is a fixed number. If Z ran over baskets of different sizes this step would not be available.

3Turning a squared length into an average

Here is the one piece of real mathematics. For a random vector z drawn from a standard bell curve — mean zero, variance one, coordinates independent — and any fixed vector v:

𝔼z ∼ N(0, I) [ exp( z⊤v ) ] = exp( ½‖v‖² )

This is nothing exotic: in one dimension it is the moment generating function of a normal, 𝔼[ezv] = ev²/2, and for a vector it is that fact applied in each coordinate and multiplied together.

Read it right to left and it says: the awkward squared-length term is secretly an average of a much friendlier one. Friendlier because z⊤v is a sum rather than a square, and sums come apart:

exp( z⊤v ) = exp( √λ · z⊤∑j∈Sφj ) = ∏j ∈ S exp( √λ · z⊤φj )

Once z is fixed, every item contributes its own separate factor. The items have stopped talking to each other. We have traded one hard coupled problem for an average over many easy uncoupled ones.

4What that does to the impossible sum

Substitute and swap the order of the sum and the average:

Z = 𝔼z [ ∑S′ ∏j ∈ S′ exp( cj + √λ z⊤φj ) ]

Now ask what the inner sum is, for one fixed z. A basket is: take exactly k1 items from category 1, exactly k2 from category 2, and so on. Since the items no longer interact, the choices in different categories are independent, so the inner sum splits into one factor per category:

Z = 𝔼z [ ∏c ekc( { wj(z) }j ∈ 𝒞(c) ) ],     wj(z) = exp( cj + √λ z⊤φj )

The quantity ek has a name — the elementary symmetric polynomial. If a category stocks 20 products with weights w1…w20 and the basket takes 3 of them, then e3 is the sum of wiwjwk over all 1,140 possible triples.

And you never enumerate those triples. There is a short recursion — essentially a knapsack dynamic program. Start with e0 = 1 and feed the items in one at a time, updating each ek ← ek + w·ek−1 from the top down. That is 20 × 3 = 60 operations instead of 1,140, and it is exact.

What has been achieved

A sum over up to 10124 baskets has become an average, over random vectors, of a product of small exact dynamic programs. The model has not changed — same score E(S), same distribution. Only the way of computing it has.

6The catch, and it is severe

Estimating an average by drawing samples works only if ordinary draws land where the mass is. Here they do not, and it is not a close call.

The quantity being averaged is exp(z⊤v), and on real baskets ‖v‖² — that is, λ‖∑φj‖² measured on the fitted model — has median 8.0. So the thing being averaged routinely swings by a factor of e8 ≈ 3,000, and nearly all of the total comes from rare z values that random draws essentially never reach. 7The fix, which is standard

Do not draw z from a bell curve centred at zero. Find where the mass actually is and draw there. Three steps:

  1. Find the peak. Locate the z at which the quantity being averaged is largest.
  2. Draw around the peak rather than around zero.
  3. Correct for having cheated. Reweight each draw by how likely it was under the distribution you should have used, divided by how likely under the one you did use. This restores an unbiased answer.

Tested against exact enumeration at a difficulty matching real baskets (‖v‖² = 9.03 against a real median of 8.0):

8Making it fast enough to train on

Accuracy was never going to be the blocker; cost was. The first working version took 328 milliseconds per basket to find the peak, and a training run needs 192 baskets × 6,000 rounds = 1,152,000 of them. That is 105 hours per fit, which is not a research tool.

Three improvements, none of them invented here.

The gradient is a known quantity, and it was being computed the stupid way

The first version handed the peak-finder no derivative, so the optimiser estimated one by nudging each of the 64 coordinates in turn — 65 evaluations per step. But the derivative has a closed form, and a meaningful one. Differentiating log ek with respect to item j's log-weight gives

∂ log ek∂ log wj = wj · ek−1(w without j)ek(w) = πj

which is exactly the probability that item j is among the k chosen. These inclusion probabilities are computable for all items at once by a stable prefix-and-suffix recursion — the same dynamic program run forwards and backwards — in O(N·k²) time, without ever dividing anything out.

Verified two ways: against brute-force enumeration of every k-subset, agreeing to 10−15; and the resulting gradient against finite differences, agreeing to 10−10. As a free check, the inclusion probabilities sum to exactly k, as they must.

The peak moves only slightly between training rounds

Each basket's peak can be remembered and reused as the starting point next time the basket is seen, so the optimiser refines rather than restarts.

The worry about multiple peaks does not materialise

The function being maximised is a concave part minus a convex part, so in principle it could have several peaks and the answer could depend on where you start. Tested with six random starting points on ten real baskets: the largest disagreement in the optimum value was 4 × 10−9. One peak, in practice.

The generation change is the largest. Once z is drawn, the categories are independent and each one reduces to "choose k items with these weights" — which the same recursion samples exactly. No draft, no swapping, no burn-in, no question about whether four rounds was enough.

10What it does not fix

  1. Deciding whether to enter a category still uses a basket-free value. At that moment there is no basket, so no basket-dependent quantity exists. This is genuinely unavoidable rather than a shortcut — but it is now confined to one place instead of running through the whole fit.
  2. The other three parts of the model are untouched. How many categories a trip enters, how many products come from each, and how many units of each — all keep their current assumptions.
  3. Nothing here has been trained yet. Everything above is measured on the existing fitted model. Whether training against the whole-basket probability produces a better model is exactly the open question, and it would be a mistake to assume it does — this project's record is that added machinery usually fails.

The honest remaining risk

The one-hour estimate is single-threaded and extrapolated from twelve baskets. The batched implementation across a whole mini-batch has not been written, and the peak-finder must stay reliable while the parameters move during training — it was tested only around the current fitted values. Neither is a reason to expect failure; both are reasons not to quote the figure as though it were measured end to end.

11Status

Feasibility established, implementation not started. In order: the batched peak-finder first, because it is the part that can still kill the idea; then log Z and its gradient; then training; then the exact sampler; then a comparison against the current model on the one question that matters — whether a discriminator can still tell generated baskets from real ones, which today it does at AUC 0.77.
