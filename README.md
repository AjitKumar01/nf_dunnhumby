# Basket model — dunnhumby "The Complete Journey"

A probabilistic model of the **whole basket**. It scores a set of products jointly, answers
price counterfactuals, and can be sampled from — so it doubles as a retail environment for
coupon and markdown policies.

```bash
git clone <this repo> && cd nf_dunnhumby
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

export NF_RAW_DIR="/path/to/dunnhumby_The-Complete-Journey CSV/"

./src/run/prepare.sh                 # raw CSVs -> model inputs   (~35 min, once)
./src/run/train.sh   my_run 40000    # train from scratch         (~8 h, 8 CPU threads)
./src/run/evaluate.sh v3_my_run_best.pt
```

That is the whole thing. The scripts set what they need and can be run from any directory.

## Results

`src/run/evaluate.sh` on the shipped checkpoint, validation split:

| | model | reference |
|---|---|---|
| set log-likelihood / basket | **−50.336** | −51.572 before this work |
| MRR (complete-the-basket) | **0.0761** | 0.0703 |
| median rank | **380** | 468 |
| MRR@5 / Recall@5 | 0.0660 / 0.1234 | 0.0575 / 0.0918 |
| MRR@20 / Recall@20 | 0.0720 / 0.1835 | 0.0667 / 0.1772 |
| own-price elasticity | **−0.681** | **−0.7725** measured from the data |
| cross-price elasticity (same sub-commodity) | **+0.044** | **+0.1351** measured from the data |
| aggregate elasticity | −0.171 | −0.121 measured from the data |
| E[n] per basket | 7.94 | 7.82 observed |

The elasticity references are estimated **independently of the model**, from an item-week
panel with item fixed effects and display/mailer controls. They are targets the model is
checked against, not quantities fitted to it.

Every row above is what `evaluate.sh` prints for the shipped checkpoint. Two notes on
reading it: the aggregate elasticity here is measured by perturbing prices and observing
`E[n]`, which runs about 35% steeper than the closed form the training log reports
(`-gb·Var(n)/E[n]` = −0.127) because the two use different variance definitions — the
projection targets the closed form, so that is the one held at −0.121. And the table's
cross-price is the row labelled *"matched to the data's definition"* in the output; the
`cross, same cat` columns beside it are a different perturbation (all purchased prices
raised at once) and are not comparable to +0.1351.

### What it does not do yet

* **Cross-price reaches a third of its target.** The price reference's width is the knob —
  measured, cross-price is −0.162 (whole assortment), +0.044 (category), +0.502
  (sub-commodity); the target sits at an effective width of ~85 products, between the last
  two. Closing it means a blended reference: elasticity fidelity, no likelihood gain.
* **Household price sensitivity carries ~0.1% of ranking.** Taste personalises, price does
  not. Coupon targeting needs the second.
* **Segment-level generation** reproduces population basket size well but compresses between
  segments, with 1–4/10 top-product overlap.
* **The shipped run was still improving** when its iteration budget ran out
  (+0.008 nats/1,000 it). Longer runs will do slightly better; a terminal learning-rate
  decay was tested and does not help (+0.009 nats, within noise).

The model in one line: a basket `S` has energy

```
E(S) = sum_j b_j  +  sum_{j<k} phi_j'phi_k  -  sum_c rho_c C(n_c,2)  -  rho_0(|S|)
```

with `P(S) ∝ exp E(S)`. The normaliser sums over every subset of the store's assortment,
which is tractable because Hubbard–Stratonovich turns the quadratic term into a
4-dimensional Gaussian integral over an integrand in which items are independent.
`docs/THEORY.md` develops this properly.

## Layout

```
src/pipeline/   raw dunnhumby CSVs -> data/ -> basket_input/
src/basket/     the model, its training loop, and every evaluation
src/run/        prepare.sh  train.sh  evaluate.sh
docs/           theory, architecture, data lineage
```

Paths are discovered, not assumed: `src/basket/paths.py` finds the repository root by
walking up from itself, so scripts work from any working directory and the tree can be
rearranged. `NF_ROOT` overrides the root, `NF_RAW_DIR` the raw CSV location.

Everything under `basket_input/`, `data/` and `out/` is regenerated by `prepare.sh` and is
not committed — except two small auxiliary inputs (`v3_beta_target.npz` 132 KB,
`v3_phimask_lift30.npy` 44 KB) that the training flags reference, so a fresh clone can train
without re-running the co-purchase scans.

## The three scripts

**`prepare.sh`** — builds every model input from the raw CSVs. Idempotent. Reads
`transaction_data.csv` (142 MB), `product.csv` and `causal_data.csv` (696 MB); the raw data
is never modified. Produces `data/`, then `basket_input/` (5,455 products, 2,066 households,
115 stores, 199,345 baskets), then the cached ragged index.

**`train.sh [label] [iterations]`** — trains the shipped configuration from scratch, in one
run. About 0.7 s/iteration on 8 threads. Writes `out/v3_<label>.pt`,
`out/v3_<label>_best.pt`, and one JSON object per evaluation to `out/<label>_metrics.jsonl`
(37 fields, including per-block gradient norms and wall clock, so a stall can be told from a
slowdown after the fact).

To continue an existing run rather than start fresh, see `docs/ARCHITECTURE.md` §7 — there
are two ways to resume that silently use the wrong learning rate, and the startup log prints
every group's rate so you can check in one line.

**`evaluate.sh <checkpoint>`** — MRR and MRR@k, then price counterfactuals, personalisation
ablations, customer segmentation and segment-level generation. Accepts an absolute path, a
relative path, or a bare checkpoint name. Writes a JSON alongside the checkpoint.

## Notes for anyone extending this

Two things in the code are load-bearing and worth knowing before changing anything.

**`V3_AFFINITY=1` selects the data partition**, and the partition sets the shape of `rho_c`.
Checkpoints are not comparable across partitions. The `src/run/` scripts export it; anything
you run by hand must too. `load_any` turns a mismatch into an explicit message.

**Checkpoints carry `model_flags`** recording properties the tensors cannot express —
`price_soft`, `price_ref`, `poly_degree`. Two different models can have byte-identical
weights; `gamma = +0.0207` is a valid price coefficient *and* a valid softplus pre-image, and
reading it wrong scales the price block 34×. Always load through `evalall.load_any`;
`stamp_flags.py` backfills older checkpoints.

Both are explained in `docs/ARCHITECTURE.md`.
